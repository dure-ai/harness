## 요약 (먼저 읽을 것)

1. **우리와 가장 가까운 연구는 DreamBench-SWE이고, 엄밀성에서는 그쪽이 앞서 있다.** 사전등록 파일 해시 고정(2026-07-03), 함정 군집 단위 순열 검정, Holm 보정, 실행 가능한 숨은 오라클, 호스팅 Mem0 블랙박스 채점까지 했다(◎). 우리가 "사전등록·결정적 채점·블랙박스 엔진"을 차별점이라 부르면 바로 반박당한다.
2. **t2의 "독립 출처 승격은 미발견"은 이번에 깨졌다.** GovMem(arXiv 2607.02579, MLiSE 2026 채택 표기)은 코딩 에이전트 궤적에서 "상관된 반복 관찰을 독립 증거로 세어 생기는 거짓 승격"을 정면으로 다룬다. 같은 에이전트 메아리, 복사 출처, 공유 도구 같은 범주와 raw frequency·unique-source 기준선을 쓴다(◎). 남는 차이는 "외부 엔진을 블랙박스로, 하류 행동(M1)으로 잰다"뿐이고, 그것도 우리 예시에 해당 계열(`normal_repeat`, `coincidence`) YAML이 없어 **아직 실측이 0건**이다.
3. **결정적(비 LLM) 채점은 이제 기본 조건이다.** DreamBench-SWE, ForgetEval, MemRiskBench(◎, "no LLM-as-judge on the pass/fail path", stale·충돌·교차 사용자 누출·철회 기억 재사용 포함), STATE-Bench 상태 단언이 모두 하고 있다.
4. **살아남는 차별점은 셋뿐이고, 모두 "범위·설계" 주장이지 "결과" 주장이 아니다.** ① 코딩 에이전트 **팀** 메모리(개인·팀 범위가 있는 다중 사용자)를 엔진 블랙박스로 보는 범위, ② 누출을 비율이 아니라 **판정 게이트**(M3=0)로 둔 설계, ③ 오염·우연·진리 변화·조건부·누출을 한 하네스에서 같은 규칙 에이전트·같은 기준선으로 보는 **조합**. 셋 다 "검색 범위 안에서 같은 조합을 찾지 못했다"까지만 말할 수 있다.
5. **10/29 전에 반드시 고칠 위협 5개**(§4): ① 표본이 아주 작고 문항이 독립이 아닌데 판정은 점추정이다(block 3문항, Wilson 구간은 문항 독립 가정), ② `sources`/`markers` 채점 비대칭이 오픈소스 비교표를 좌우한다, ③ 규칙 에이전트 지표를 "에이전트 오행동률"로 부르고 있다, ④ 시나리오 작성 편향과 BM25 맞춤 판정선(`all_store` M1=1.000이 구조적으로 정해짐), ⑤ 오픈소스 엔진 비교의 공정성 조건(가상 시계·`flush` 시간·인프라 오류=판정 불가) 미표시. 다섯 개 모두 **기존 결과물로 계산하거나 문구로 고칠 수 있는 S급**이다.
6. **경로**: 10/29는 "벤치마크 결과"가 아니라 **"검증 도구 v0.1 + 파일럿 수치(판정 불가 표시 포함)"**로 발표한다. 11월에 표본·계열 확충, 군집 통계, `rules_file` 기준선을 넣는다. 12월에 규칙 에이전트 교정 연구(LLM 에이전트 2~3종과 순위 일치도)를 한다. 이 교정 연구가 차별점 ②·③을 "결과" 주장으로 바꿀 수 있는 유일한 길이다.

판정 범주:
- **진짜 차별점**: 근접 선행 연구가 있어도 핵심 요소가 빠져 있고, 반론을 견딘다
- **기본 조건(table stakes)**: 이제 신뢰할 만한 메모리 평가라면 다 갖춰야 하는 것. 갖추지 않으면 감점이지만 갖춰도 가점은 아니다
- **이미 다른 곳이 함**: 같은 양을 같은 방식으로 재는 선행 연구가 있다
- **위험한 주장**: 말하면 사실과 다르거나, 우리 실측이 뒷받침하지 못한다

### 3.1 우리가 말해도 되는 것

1. "주요 지표는 LLM judge 없이 결정적으로 채점한다. 같은 시드로 두 번 돌리면 결과 파일이 바이트 단위로 같다." (t3 실측)
2. "판정 기준(전부 저장 기준선 대비 M1·M2, 누출 0)은 결과를 보기 전에 설정 파일로 고정했다." 단 해시를 git 태그로 남긴 경우에만 말한다.
3. "코딩 에이전트 **팀** 메모리, 즉 개인/팀 공개 범위가 있는 다중 사용자 기록을 대상으로, 오염·우연·진리 변화·조건부 사실·누출을 같은 에이전트 규칙과 같은 기준선으로 비교하는 하네스다. 조사한 범위(약 60건 이상)에서 이 조합을 한 곳에서 하는 평가는 찾지 못했다."
4. "누출은 비율이 아니라 판정 게이트다. 한 건이라도 새면 탈락이다." 항상 "0/n, 95% 상한 약 3/n"을 같이 적는다.
5. "에이전트는 일부러 규칙 기반으로 고정했다. 엔진 차이만 분리하려는 선택이고, LLM 에이전트와의 일치는 아직 검증하지 않았다(검증 계획 있음)."
6. "가장 가까운 선행 연구는 DreamBench-SWE, Memory Trust Gap, GovMem, MemRiskBench, GateMem이다. 우리는 그들이 다루지 않은 팀 범위·누출 게이트·엔진 블랙박스 비교를 더한다." (관련 연구 슬라이드)
7. "외부 연구도 메모리 엔진이 메모리 끈 조건을 유의하게 넘지 못한 사례를 보고한다(VibeMemBench: 4개 엔진 × 3개 모델 중 유의하게 넘은 조합 0개, 점추정 11/12가 그 이하)." 그래서 "틀린 기억을 막는가"를 따로 재야 한다는 동기로 쓴다.
8. "LLM judge는 모호한 오답을 관대하게 통과시킨다는 감사가 있다(LoCoMo 감사, 비동료심사)." 출처 성격을 함께 적는다.
9. 수치는 "규칙 에이전트 기준 틀린 근거 채택률(M1)", "맞는 근거 활용률(M2)"로 부르고, "파일럿(dev, draft 포함, n=…)"을 붙인다.

### 3.2 우리가 말하면 안 되는 것

1. "행동 수준에서 틀린 기억을 재는 것은 우리가 처음" → DreamBench-SWE, Memory Trust Gap, STALE, Sleeper가 반례.
2. "사전등록한 메모리 벤치마크는 처음" → DreamBench-SWE.
3. "독립 출처 승격을 평가하는 것은 우리뿐" → GovMem. 게다가 우리 실측 0건.
4. "결정적 채점이 우리 차별점" → MemRiskBench, DreamBench-SWE, ForgetEval.
5. "엔진의 승격·강등 결정을 채점한다" → 설계상 관찰 지표일 뿐. 거짓이다.
6. "자기강화(echo)를 측정한다" (판정 수치로) → 되먹임은 판정 제외, recall 이벤트 없음.
7. "M1 = 에이전트의 오행동률", "실제 에이전트가 틀린 기억으로 행동하는 비율" → 규칙 에이전트 기준 노출 지표다.
8. "누출 0건 = 안전" → 3/n 상한, 의역 누출 미검출.
9. "엔진 A가 B보다 낫다"(순위) → 표본 n이 작고, 동률 규칙이 추이적이지 않고, 엔진이 2개뿐이다.
10. 요약 문서에서 온 것: "토큰 비용 최대 90% 절감", "LoCoMo 고득점 → 에이전트 환경 40~60%", "Agent-as-a-Judge가 실패 탐지 수 배", "Meta-Harness ICML 2026", "Rethinking COLM 2026", "4W taxonomy", "Cognee가 가장 많이 채택".
11. "Mem0이 DreamBench-SWE에서 53.9%" (설정 없이) → literal-storage 설정이고 기본 설정은 게이트에서 탈락했다.
12. "철회 지연은 우리만 잰다" → 미검증(D15).
13. "LLM 시뮬레이터는 9%p나 흔들리니 규칙 에이전트가 더 낫다" → 그 연구는 사용자 시뮬레이터 연구이고, 규칙 에이전트의 타당도를 보여 주지 않는다.

### 4.1 반드시 고칠 것 5개 (발표 전)

| 순위 | 위협 (출처) | 왜 헤드라인을 무효로 만드나 | 가장 싼 신뢰할 만한 완화 | 노력 |
|---|---|---|---|---|
| **MF1** | **표본이 아주 작고 문항이 독립이 아닌데 판정은 점추정**(t3 T3·T14, t8 §1, Miller ◎) | 예시 기준 읽기 전용 block은 3문항이다. 판정선 "M1 ≤ 0.5"에서 1/3은 통과하고 2/3은 탈락한다. 즉 **문항 하나가 합격을 가른다.** n=3이면 Wilson 구간이 [0, 0.561] 같은 폭이다. 같은 시나리오 안의 문항은 군집이라 실제 불확실성은 더 크다(군집 SE는 최대 3배 이상, ◎ V4). M1 차이는 아예 검정하지 않는다(t3 T3). 독립 가정 문항 수 계산으로도 M1 0.40 대 0.20을 구별하려면 엔진당 약 80문항이 필요하다(○ t8 자체 계산, 내가 공식으로 재확인: 7.84×0.40/0.04≈78) | ① 판정을 **3상태**(통과/탈락/판정 불가)로 바꾸고, 시나리오 군집이 11개 미만이거나 문항이 30개 미만이면 "판정 불가(표본 부족)"로 표시한다(○ t8 [11]). 코드 변경이 부담이면 리포트 문구와 발표 표에서만이라도 한다. ② M1·M2 옆에 n, 시나리오 수, 구간을 항상 적는다. ③ 가능하면 `selection.py`에 시나리오 단위 군집 부트스트랩 구간을 추가한다(기존 부트스트랩 함수를 M1에도 적용) | S (문구) ~ M (코드) |
| **MF2** | **`sources`/`markers` 채점 비대칭**(t3 T2·T9, 설계 §4.5) | 오픈소스 비교표가 바로 이 축에서 갈린다. 출처를 돌려주지 않거나 기억을 의역·병합하는 엔진은 마커가 사라져 → 기권 → **M1은 좋아 보이고 M2만 깎인다**(거짓 안전). 출처를 다는 엔진은 본문을 왜곡해도 통과한다. 두 오픈소스 엔진의 출처 지원이 다르면 비교표는 엔진 품질이 아니라 출처 지원 여부를 보여 준다 | ① 엔진별 **"markers로 판정한 문항 비율"**과 "출처 없는 결과 비율"을 표에 같이 싣는다(이미 있는 결과에서 계산 가능). ② 민감도 분석: markers 판정을 모두 기권으로 바꿨을 때의 M1·M2를 병기한다. ③ 두 엔진의 `info().sources` 지원 여부를 표 머리에 적는다. 비율이 높은 엔진의 M1에는 "하한이 아닐 수 있음" 주석 | S |

[참, 거짓]이면 안전이고 [거짓, 참]이면 FP다 | ① 이름을 "규칙 에이전트 기준 틀린 근거 채택률"로 바꾼다. ② 이미 계산하는 **오염 노출률**(목록 어디든 틀린 근거가 있는 비율)을 M1 옆에 **상한**으로 병기한다. 이렇게 "첫 결과만 따름"(M1)과 "목록 전체에 속을 수 있음"(노출률) 사이의 구간으로 보여 준다. ③ "LLM 에이전트와의 일치 검증은 11~12월 계획"을 슬라이드에 적는다(t8 §5.1 권고와 같음) | S |

### 5.3 교정 연구 결과에 따른 분기 [판단]

- 순위 일치(τ가 높음): "규칙 에이전트는 엔진 순위 예측에 충분하다"를 주장할 수 있고, D14·D17이 결과 주장이 된다. 이것이 DreamBench-SWE 대비 우리 비용 우위(LLM 호출 0, 초 단위 실행)를 정당화한다.
- 순위 불일치: 어느 규칙(첫 결과만 따름, 마커 판정, 기권 처리)이 틀렸는지 찾아 에이전트 규칙을 고치거나, 하네스를 "LLM 에이전트 평가 전 빠른 선별기"로 재포지셔닝한다. 어느 쪽이든 그 결과 자체가 발표 가치가 있다(규칙 대 LLM 에이전트 직접 비교는 문헌에 없다).
