### 2.4 두 가지 재생 모드와 시간표

- 공통: 이벤트와 문항을 `(t, 종류, 순번)` 힙에 섞어 가상 시간 순으로 흘린다. 같은 시각이면 이벤트가 먼저 (`replay.py:18, 114-141`, D §6.1 L305). 엔진 `info().virtual_clock`이 참이면 매 단계 전에 `tick(t)`, 문항마다 `flush()` 후 `search` (`replay.py:360, 370-371, 384-388`). 이름공간 = `"{run_id}:{HMAC(키,"ns:"+시나리오 id)[:16]}"` (`replay.py:40-54`). 결과는 `k`(설정 5, 문항별 덮어쓰기 가능)개까지 (`replay.py:396`, `model.py:120`).
- **읽기 전용 (`read_only`)**: 문항 결과는 채점만 하고 버린다. 모든 엔진이 완전히 같은 이벤트를 받는다. M1·M2·M3는 이 모드의 결과로만 낸다 (D §6.2 L311).
- **되먹임 (`feedback`)**: 각 문항 뒤 `feedback_events`가 (a) 행동 기록 (질문+5분, 틀에서 본문·`fact`; 기권이면 `abstain` 틀), (b) 결과 기록 (`on_false` 틀: 질문+1일 / `on_true`: 질문+0분, 행동 기록보다 앞서지 않게 상향, `refs`=따른 결과의 `sources`)을 만들어 시간표에 다시 넣는다 (`replay.py:231-295, 399-408`, 지연 기본값 `config.py:59-78`). 생성 이벤트 id는 일반 시나리오 id와 같은 `e{n}` 형식이지만 완전히 구별 불가능하지는 않다 (`replay.py:170-193`, D L325). `mode: feedback` 시나리오는 되먹임으로만 돌고, 점수는 헤드라인과 섞이지 않는다 (`validate.py:229-231`, `metrics.py:221-235`).

### 2.5 규칙 기반 에이전트: 결정 규칙과 한계

**규칙** (`agent.py:1-6, 39-106`, D §7.1-7.2 L332-348):
1. 결과 목록을 위에서부터 훑는다. 각 결과의 **근거 사실 집합**(`result_basis`)이 비어 있지 않은 **첫 결과**를 따른다. 없으면 기권.
2. 근거 집합: (a) `sources`가 있으면 *질문 시점까지 엔진에 `record`된* 이벤트의 숨은 `fact` 전부 (`about` 밖 포함). 그중 `about`에 든 게 하나도 없으면 무관(빈 집합). 둘 이상이면 본문에 마커가 나타나는 사실로 좁히되, 좁힌 집합에 `about` 사실이 없으면 좁히지 않는다 (`agent.py:71-82`). (b) `sources`가 비면 `about` 사실 중 마커가 본문에 있는 것 (`agent.py:69-70`).
3. 판정: 근거 중 하나라도 시점·맥락에서 거짓이면 틀린 근거 ("섞인 근거는 보수적으로 틀림", D L346).
4. 엔진이 붙인 `meta`, 본문 속 "rumor" 같은 단어, 점수는 보지 않는다 (D L336, `agent.py:5-6`).

**실제 LLM 에이전트와 달리 모델링하지 못하는 것** (코드·설계로 확인되는 범위):
- 목록 전체를 한꺼번에 읽고 충돌을 조정하지 못한다. 첫 관련 결과만 따른다 (`agent.py:102-106`). 순위가 [참, 거짓]이면 안전, [거짓, 참]이면 FP. 반면 실제 에이전트는 둘 다 보고 판단하거나 둘 다에 속을 수 있다. 오염 노출률(`metrics.py:242-245`)만이 이 차이를 부분 반영.
- 본문의 의미를 읽지 못한다. "이전에는 X, 이제는 Y로 대체됨" 같은 시간 주석, 경고, 신뢰도 표시를 무시한다 (D L336). 그러므로 주석으로 가치를 만드는 엔진은 이득이 없고, 이런 결과가 두 사실의 마커를 모두 가지면 오히려 틀린 근거가 된다 (`agent.py:78-82`).
- `sources`가 있으면 본문 정확성을 검증하지 않는다. 요약이 왜곡돼도 출처 id만 맞으면 통과 (`agent.py:71-82`).
- 의심·확인·재질문·질의 재작성·다단계 검색이 없다. 문항당 검색 1회, 관련 결과가 있으면 항상 행동한다 (`agent.py:102-106`, `replay.py:380-396`). 관련 결과가 없을 때의 기권은 "직접 탐색해 찾음"이라는 되먹임 템플릿으로만 표현된다 (D L321).
- 무관하지만 그럴듯한 결과에 속지 않는다 (무관 결과는 건너뜀: `agent.py:76-77`).
- 응답 품질·말투·장황함에 영향받지 않는다 (의도적: 편향 제거).
- 침묵이 M1을 보상한다: block 문항에서 기권은 BLOCKED (`scoring.py:43-44`). 그래서 `none`의 M1은 0이다 (자가 검증 실측: `none m1=0.000`). M2 하한(`all_store`−0.10)이 이를 막는 유일한 장치다 (`selection.py:101-105`).
- 같은 엔진·같은 시나리오면 흐름이 항상 같다 (D L326). 인간/LLM 에이전트의 변동성은 없다.

### 2.6 기준선, 자가 검증, 속도·규모 (실측)

**기준선 4종** (`engines.py:11-47`, D §9.1 L421-430):
- `none`: 항상 빈 목록 (`simple.py:42-52`).
- `all_store`: 볼 수 있는 모든 이벤트를 BM25로 순위화해 상위 k (`simple.py:55-77`, 토큰화·BM25 `text.py:7-95`). 판정 기준선.
- `repeat_n`: 볼 수 있는 이벤트 중 Jaccard ≥ τ(0.5)인 유사 이벤트가 N(3)개 이상인 것만 (`simple.py:80-110`). 출처 독립성은 보지 않음.
- `oracle`: 숨은 라벨을 읽어 `about` 중 지금 참인 사실마다 가장 최근의 볼 수 있는 이벤트 (`baselines/oracle.py:9-53`).
- 진단용 `all_store_noacl` (권한 무시, 리포트에 안 나옴) (`engines.py:41-42`).

**자가 검증** (`selfcheck.py:94-137`, D §9.2 L432-444): `no_errors`, `oracle_perfect`(M1=0, M2=1, M3=0), `none_empty`(0,0,0), `all_store_max_m1`(M1>0이고 최대), `repeat_n_poison`/`repeat_n_echo`(해당 계열이 있을 때 `repeat_n` M1 > `oracle`). `run`은 항상 자가 검증부터 하고 실패하면 엔진 평가를 막는다 (`cli.py:291-294`). 시나리오 단위 변별력 검사 `scenario check` (`selfcheck.py:140-172`): `oracle`이 모든 block·promote를 맞히고 누출이 없어야 함(아니면 오류), `all_store`가 block에서 FP를 하나도 안 내면 `too_easy` 경고, 누출 문항은 `all_store_noacl`이 실제로 누출해야 함.

### 2.7 통계 (D §8.3 L398-415)

- 모든 비율에 Wilson 95% 구간 (`stats.py:8-26`, 비율 객체 `stats.py:29-48`). 예: n=3이면 `1.000 [0.439, 1.000]`, `0/3`이면 `[0, 0.561]` (실측 리포트).
- 판정용 M1·M2는 문항을 모두 합친 pooled 비율 (`metrics.py:92-97`). 반복 실행(LLM 엔진은 기본 3회: `config/eval-v0.1.yaml:17`)이면 M1·M2는 회차 평균, M3는 가장 나쁜 회차, 오류는 합집합, 나머지 비율 지표는 회차별 분자·분모를 합산 (`selection.py:161-206`). **예외: M1·M2 신뢰구간과 순위 부트스트랩은 첫 회차 기준** (D L404, `cli.py:325`).
- 엔진 간 차이: 시나리오 단위 부트스트랩 (기본 10,000회, 시드 20261019 고정), 같은 시나리오 인덱스로 두 엔진을 짝지어 재표본 (`stats.py:72-99`, `config.py:33-42`). **promote TP 비율의 차이만** 검정한다 (`selection.py:225-245`). 두 엔진 모두 promote 문항이 있는 공통 시나리오만 표본 (`selection.py:240`).
- 순위 (`selection.py:326-366`): 판정 통과 엔진만; M2 정렬; 인접 쌍의 M2 차이 구간이 0을 포함하면 동률 → `m1 → shallow_fix → retraction → reach → context_chars` 순으로 가른다 (`selection.py:15, 258-279`). 후보 엔진만 순위를 매기고 기준선은 점수와 판정만 보고 (D L414). 안정 삽입 정렬 + 쌍별 비교 (`selection.py:347-353`).

### 2.9 생성·검토 파이프라인, 오픈소스 어댑터 (이 커밋 기준)

- **설계** (D §11 L463-485): 원칙 "구조는 코드, 내용은 LLM, 승인은 사람". 7단계: ① `harness traces fetch`(Open-SWE-Traces, CC BY 4.0, Python 저장소만) ② LLM이 사실 후보 추출(원문 인용·메시지 번호 필수) ③ 인용 검사(코드) ④ 계열 틀 적용(코드, 시드 고정) ⑤ LLM이 본문·질문·마커 작성(영어) ⑥ 자동 검증(형식·짝·기간·마커·금지 사실 재언급·변별력) ⑦ 사람이 `approved`/`rejected`. 검토 CLI `harness review list/show/set`, 빈 틀 `harness scenario new --family`. LLM 호출은 입력 해시로 캐시, `llm_model`·`prompt_version` 기록.
- **이 커밋의 구현**: 위 CLI는 **없다** (`cli.py`에 `scenario check`, `selfcheck`, `run`만). 구현된 것은 *검토 상태 모델*(`Review`, `Provenance`: `model.py:131-145`), `approved`만 평가에 넣는 로더 (`load.py:79-92`), 출처별(human/llm/generator) 결과 표 (`metrics.py:118-124`)뿐이다. 이 커밋 시점의 팀 합의 상태는 D L561 "남은 것은 생성 파이프라인과 검토 CLI, 오픈소스 어댑터, core 런타임 어댑터다."
- **오픈소스 어댑터** (D §10 L448-459): Hindsight·Graphiti를 Docker로, REST로 호출, 스코프는 bank/group_id로 대응, 3회 반복. **이 커밋에는 코드가 없다.** 다른 브랜치 `feat/oss-adapters`에 `oss/hindsight.py`, `engines/docker/{hindsight,mem0}/compose.yaml`이 있으나 내용은 이 조사 범위 밖.

- 일정 대비 현황: 설계 §17 L555-557은 10/23에 생성 파이프라인, 10/24~25에 어댑터를 요구하지만 이 커밋(10/22~24 문서 정리)에는 핵심 하네스만 있다.

## 4. 우리 접근의 타당성 위협 (코드에서 확인된 한계)

각 항목은 *증거*를 달았다. 심각도는 내 판단이다 (높음 = 결과 해석을 직접 흔듦).

**T1. 규칙 기반 에이전트의 현실성 (높음)**
- 증거: 첫 관련 결과만 따름 (`agent.py:102-106`); 본문 의미·경고·시간 주석 무시 (`agent.py:5-6`, D L336); 문항당 검색 1회·재질문 없음 (`replay.py:380-396`); 혼합 근거는 무조건 틀림 (`agent.py:78-82`, D L346).
- 영향: M1·M2는 "엔진이 *첫 번째 관련 결과* 에 무엇을 놓았는가"의 지표다. 목록 구성이 같아도 순서가 다르면 점수가 크게 다르고 (순위 민감도), 반대로 실제 모델은 목록 전체를 읽고 덜/더 속을 수 있다. 오염 노출률이 보조 신호이지만 판정에는 안 쓰인다. 과거 + 현재를 *함께 주석과 함께* 건네는 엔진(예: "A였으나 B로 변경")은 이 에이전트로는 불리하다 (두 마커/출처 → 틀린 근거).

**T2. sources 있음 / 없음의 비대칭 채점 (높음)**
- 증거: `sources` 있으면 본문 미검증 (`agent.py:71-82`), 없으면 마커 부분 문자열 (`agent.py:69-70`), 기권은 block에서 안전 (`scoring.py:43-44`), 출처 없는 엔진은 판정 문자열로 채점 (D L179). README의 인정: 이미 기록된 id만 돌려주는 엔진을 구별 못 함 (R L163).
- 영향: (a) LLM이 기억을 의역·병합하는 엔진(출처 없음)은 마커가 사라져 근거가 비고 → 기권 → M1은 좋아 보이고 M2만 깎인다 (거짓 안전). (b) 출처를 *다는* 엔진은 본문을 아무리 왜곡해도 통과 (요약 표류 미검출). (c) 부정·대체 문장이 마커를 포함하면 오히려 틀린 근거가 된다. 출처 유무가 엔진 설계의 결과일 뿐 성능이 아닌데 점수에 영향을 준다 (리포트는 "출처 없는 결과" 비율만 보고: `metrics.py:246`).

**T3. 시나리오 규모가 너무 작고, 신뢰구간이 낙관적 (높음)**
- 증거: 예시 평균 3.8 이벤트/2.4 문항, 총 문항 12 (§2.1 실측). Wilson 구간은 문항을 독립으로 가정 (`stats.py:8-26`, `metrics.py:92-97`) 하지만 `echo`의 block 3문항은 같은 질문·같은 시나리오·순차 의존 (`echo_stale_owner.yaml:25-60`). 부트스트랩은 promote TP만, 첫 회차만 (`selection.py:225-245`, D L404): **M1 차이는 검정되지 않는다** (M1은 동률 해소 기준일 뿐: `selection.py:15`).
- 영향: 판정 임계(M1≤0.5×기준선, M2≥기준선−0.10)는 문항 수십 개 미만이면 한두 문항의 뒤집힘에 좌우된다. dev 세트는 비어 있어 실제 표본 수를 알 수 없다 (`scenarios/dev/` 빈 디렉터리).

**T4. 시나리오 작성 편향·과적합 (높음)**
- 증거: 시나리오·계열·기준선·판정 기준을 같은 팀이 설계 (D §14-4 L514 담당 미정); 예시는 전부 `author: llm`, `status: draft`; 10계열 중 5개만 YAML 예시 존재 (`tests/test_examples.py:23-27`); 계열 틀 강제 검증이 없음 (`validate.py:229-247`은 모드·짝만) → 손으로 쓰면 계열 라벨이 내용과 다를 수 있고 계열별 표가 오도될 수 있다.
- 영향: 팀 엔진이 "우리 10계열"에 맞춰 개발되면 계열 테스트는 통과하지만 일반화는 알 수 없다. 방어(봉인 test 세트)는 설계에 있으나 test 세트와 담당자가 없다. 사실의 모양이 코딩 도메인(빌드 명령, 모듈 소유권, `fix=root/workaround`: `model.py:45-51`)과 영어(D L475, 모델 `language="en"`: `model.py:170`)에 한정.

**T5. BM25 기준선에 묶인 판정선과 어휘 중복 설계 (중간~높음)**
- 증거: 합격선이 `all_store`(BM25) 상대값 (`selection.py:96-105`). 변별력 검사가 `all_store`가 FP를 내도록 시나리오를 거른다 (`selfcheck.py:163-165`), 자가 검증도 `all_store` M1>0 요구 (`selfcheck.py:68-74`). 예시 이벤트가 질의문을 그대로 본문에 넣는다 (`single_source_poison_test_cmd.yaml:15-21`의 "Which command runs the tests? …", `conditional_db_isolation.yaml:19-24`). 실측으로 `all_store` M1 = 1.000, M2 = 1.000.
- 영향: 기준선 M1이 구조적으로 높게 설계되어 있어 "M1 ≤ 0.5×기준선"이 사실상 "M1 ≤ 0.5"로 굳는다. 의미(임베딩) 검색 엔진이 BM25 중심 어휘 겹침 시나리오에서 유리/불리한지 알 수 없다. 코퍼스가 작아 `k=5`가 코퍼스 전체를 덮으므로 (실측 결과 길이 4~5 = 이벤트 수) 순위 품질은 변별되지 않는다 (T10과 연결).

**T6. 사실 모델의 단순함 (중간)**
- 증거: 이벤트 하나 = 사실 하나 (`model.py:72`), 사실은 시간×조건의 이진 참 (`world.py:9-29`), 신뢰도·부분 진실·출처 간 충돌 해소 규칙 없음, 사용자는 한 팀 (D L291).
- 영향: 종합·다중 홉·확률적 지식·"의견이 갈리는 지식"은 시험할 수 없다 (§1.2 10b).

**T7. 가상 시계 미지원 엔진의 시간 계열 (중간)**
- 증거: `tick`은 `virtual_clock=True`일 때만 (`replay.py:370, 384`), 아니면 리포트에 "주석 필요"만 (`report.py:471-472`). 지연은 문항 시각에서만 측정 (`metrics.py:170-181`).
- 영향: 실제 시계를 쓰는 엔진은 2026-10 이벤트를 "지금" 기준으로 해석할 수 있어, 시간 계열(truth_change, 철회 지연) 결과가 엔진 능력이 아니라 시계 처리 차이일 수 있다. 주석이 사람 몫으로 남아 있어 비교표에서 빠질 위험.

**T8. 되먹임 모드는 가장 약한 고리 (중간~높음)**
- 증거: 판정·순위 제외 (D L316, `metrics.py:221-235`); recall 이벤트 없음 → 이를 쓰는 엔진은 방어 장치를 못 쓴다 (D L158, §14-16 L526); 생성 이벤트가 구별 가능 (행동 기록의 질문+5분 시각과 같은 user/session/repo 등: D L325); 앞 문항 행동에 따라 생성 기록 수가 엔진마다 달라진다 (D L325, 실측 `echo` 3 vs 6) → "모든 엔진에 같은 입력" 원칙이 이 모드에서는 성립하지 않는다 (D L326: 기준은 "같은 세계 + 같은 에이전트 규칙").
- 영향: 요약 문서가 지적한 "상호작용 루프" 영역(echo, 실패 학습)의 결과는 해석에 부분적으로만 쓸 수 있다. `failure_feedback` 예시가 없어 실제 실행 경로가 한 번도 검증되지 않았다.

**T9. 요약·LLM 의미 판단 불가로 인한 맹점 (중간)**
- 증거: T2와 같음; 의역 동치, 요약 왜곡, 부정 표현 처리 불가 (`agent.py:28-36`). 누출도 `secret_markers` 문자열 의존 (`scoring.py:96-103`).
- 영향: 요약 압축(Summary Drift)·의역 기반 유출은 측정하지 못한다. 이것이 상용 메모리 엔진의 핵심 위험인데 현재 점수에 반영되지 않는다.

**T10. 순위·규모의 현실성 부족 (중간)**
- 증거: 코퍼스가 `k` 이하 (§2.1 실측), 잡음 0개, 길이 부풀리기 비목표 (D L30). 합성 규모 시험(§2.6)은 기준선만 측정했을 뿐 실제 엔진 ingest 비용·시간은 측정된 바 없다. `flush()`는 시간 측정 밖 (`replay.py:386-389`). 직렬 실행, 스냅샷 없음 (`cli.py:219-241`).
- 영향: 장기·대규모 환경에서 엔진이 보이는 행동(검색 노이즈, ingest 지연, 요약 압축)이 점수에 나타나지 않는다. 실제 엔진을 3회 반복 × 시나리오 N개 돌리는 비용은 아직 추정할 수 없다.

**T11. 오류·인프라 처리의 거침 (중간)**
- 증거: 모든 예외가 엔진 결함과 같은 오류, 오류가 하나라도 있으면 판정 불가 (`selection.py:116-117`), 타임아웃·재시도 없음 (`replay.py:375-377, 393-395`).
- 영향: 일시적 Docker/네트워크 오류 하나로 후보 전체가 탈락 처리될 수 있다. 반대로 하네스 코드 예외는 잡지 않는다 (`replay.py:380-382`): 하네스 버그는 드러나지만 전체 실행이 중단된다.

**T12. 이름공간·id 격리 신뢰 (낮음~중간)**
- 증거: `reset(namespace)`를 믿고 (D L535), 기록되지 않은 id는 무시 (`scoring.py:76-77, 89-93`; `agent.py:73-75`), 시나리오마다 이벤트 id가 `e1`부터 시작 (`scenarios/examples/*.yaml`).
- 영향: 엔진이 이전 시나리오의 잔존 데이터를 돌려줘도 id가 겹치면 정상 근거로 보일 수 있고, 겹치지 않으면 조용히 무시된다. 격리 실패 *검출*은 없다.

**T13. 블라인드의 구멍 (낮음)**
- 증거: `results.jsonl`은 블라인드가 아님, 엔진이 정한 문자열(버전, 설정, 오류)은 못 가림 (D L497).
- 영향: 팀원 엔진 평가를 팀원이 보면 후보를 알아볼 수 있다. 완화: `report.md`·`summary.json`만 내보낸다 (D L497).

**T14. 통계의 한계 (중간)**
- 증거: 다중 비교 보정 없음, 첫 회차로 구간·순위 계산 (D L404), M1 차이 미검정 (T3), 부트스트랩 표본이 공통 시나리오 중 promote가 있는 것만 (`selection.py:240`).
- 영향: 엔진 수가 늘면 우연한 순위가 늘고, 반복 실행의 정보가 구간에 반영되지 않는다.

**T15. 문서·코드 정합성 (낮음)**
- 증거: 설계서는 생성 파이프라인·검토 CLI·OSS 어댑터를 현재형으로 기술하지만 (D §10-11) 이 커밋에는 코드가 없다 (§2.9); "테스트 303개" (D L561) vs 실제 수집 458개.

## 5. 결론용 요약 (강점·공백)

**강점 TOP 6** (요약 문서 대비)
1. **결정적 채점 + 재현성**: LLM 심판 편향·비결정성을 제거하고, 같은 시드에서 `results.jsonl` 바이트 동일, 설정·세트 해시·버전 기록, 사전 등록·블라인드·봉인 (§1.1 #6-7, §2.8).
2. **시간 갱신/모순·철회 측정**: 참 구간·조건 기반 진실, 철회/반영 지연, 얕은 지식 고착률 (§1.2 10a).
3. **행동 기반 메모리 평가**: "회상 정확도"가 아니라 "틀린 기억을 *근거로 행동*했는가"를 M1/M2로 잰다 (`scoring.py:22-47`), 정답 경로(골든 트래젝터리)를 강제하지 않음.
4. **기억 중독·메아리 계열**: 단일 출처 주입, 우연 반복, 되먹임 자기 강화를 별도 계열로 시험하고, `repeat_n`·`oracle`·`none`·`all_store` 기준선과 자가 검증(`selfcheck.py:94-137`)으로 하네스 자체의 건전성을 매 실행 점검.
5. **테넌트·권한 격리 M3**: 모든 문항·모드에 누출 검사, 진단 기준선으로 문항 유효성까지 검증, 저작 시 비밀 마커 배타성 검사 (§1.2 #17).
6. **신뢰할 수 있는 입력 경계**: 숨은 라벨 분리, 이름공간 HMAC 은닉, 시나리오 저작 검증(마커 오염, 짝 규칙, 중복 문항 등), 빠른 실행(기준선 5 시나리오 0.16초)으로 CI 통합 가능한 스모크 경로.

**공백 TOP 6**
1. **규칙 기반 에이전트의 현실성**: 첫 관련 결과만 따름, 본문 의미 무시, 재질문 없음 (T1) — "행동 기반"이지만 행동 모델이 단순.
2. **요약 표류·의역·종합 미측정**: `sources`가 있으면 본문 미검증, 출처 없는 엔진은 마커 의존 (T2, T9, §1.2 10b·14).
3. **규모·NIAH 대응 부재 + 재생 비용 장치 없음**: 이벤트 평균 3.8개, 잡음 0, `k`≥코퍼스; 스냅샷·캐시·병렬 없음; 10M 토큰 규모 미검증 (T10, §1.2 #11-12).
4. **망각(decay)·삭제(GDPR)·모델 교체 강건성**: 라벨·시나리오·계약 메서드 모두 없음 (비목표 포함) (§1.2 10c, #20, #22).
