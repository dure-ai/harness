# Agent instructions

A harness that evaluates memory engines for AI agents. Scoring uses no LLM and the same input gives the same output.

Read [CONTRIBUTING.md](CONTRIBUTING.md) first. This file adds what agents tend to get wrong. For the structure of the code, read [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Commands

```bash
uv sync --extra core            # install; without the core extra, basedpyright and the bridge tests fail
uv run ruff check src tests
uv run basedpyright src
uv run pytest -q -W error       # CI treats warnings as errors
uv run harness scenario check <path>   # after changing a scenario
```

Run all of the first four before you commit. Do not assume a failure was already there; `main` is kept green.

## Invariants

- **No randomness and no LLM on the scoring path.** Iterate in sorted order so results never depend on hash order.
- **Do not pass hidden labels to an engine.** Before adding a field to `Event` or `Query`, check that it cannot leak the answer.
- **Values that affect scores live in `config/eval-v0.1.yaml`,** not in code. Changing one means raising `version` and re-measuring every engine, so ask before you do.
- **A new engine instance per scenario.** State that carries over between scenarios corrupts the results.
- **Do not approve scenarios by editing `review.status`.** Approval goes through `uv run harness review set`, which records the hash, and it is a human decision.
- **Do not commit `runs/`** or any API key or model credential.

## Issues and pull requests

You may open issues and pull requests and write their descriptions when the user asks you to.

- **Issues**: the forms in `.github/ISSUE_TEMPLATE/` do not apply when you create an issue through the CLI or the API. Pick the matching form and reproduce its sections as headings in the body.
- **PR description**: start from `.github/PULL_REQUEST_TEMPLATE.md`. Keep every section and every checkbox, including the ones you leave unchecked.
- **PR title**: `type(scope): description`. Allowed types are in [CONTRIBUTING.md](CONTRIBUTING.md#pull-requests). The title becomes the commit subject on `main`.
- **Link the issue** with `Fixes #123`, or `Part of #123` when the PR does not finish it.
- **AI disclosure**: check "AI assistance was used to create this PR" and fill in the tool name.
- **No AI attribution anywhere else.** Do not add `Co-Authored-By` or any other trailer naming a model to a commit, and do not add a "Generated with" line to a PR description.
- **Check only what is true.** Leave "Tests added or updated" unchecked if the PR has no test changes.
- **Write in English** in issues, PR titles and descriptions, commit messages and code comments.

## Writing for the reader

The PR description becomes the commit body, so it is read by people who never saw this conversation.

- Describe the final change and the reason for it. Leave out what you tried first, the order you worked in, and anything the user said to you.
- State what you verified and how. If you did not run something, say so instead of implying it passed.
- Keep comments in code about why, not what, and never about what the code used to be.

## Changing this file

Keep it short. Add a rule only when it is specific, not obvious from the code, and has gone wrong more than once. Do not add descriptions of the code layout; they go stale and belong in `docs/`. Do not edit this file as part of other work: propose the addition in the PR description and let a reviewer decide.
